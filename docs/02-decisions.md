# 02 — Журнал решений (ADR)

Формат: только дописываем. Решение не удаляется — если передумали, пишем новое со статусом «отменяет ADR-XXX».

---

## ADR-001 — Никаких галочек соблюдения диеты

**Статус:** принято

**Контекст.** Изначально планировалось отмечать каждый съеденный приём пищи для расчёта процента соблюдения.

**Решение.** Убрано. Остаются только операционные галочки: «закупился», «приготовил».

**Обоснование.** Взвешивание — ground truth, галочки — прокси. При регулярных замерах прокси избыточен. Плюс галочки провоцируют вранье самому себе, после чего цифры теряют смысл и человек отваливается.

**Последствия.** Прогноз строится только на фактических замерах. Сорвался — вес покажет сам, прогноз сдвинется.

## ADR-002 — Талия как primary-метрика

**Статус:** принято

**Контекст.** Цель формулируется и по весу (80 → 75 кг), и по талии (91 → 87 см). Они не приходят одновременно.

**Решение.** Талия — primary. Вес — secondary, используется для расчёта дефицита и прогноза.

**Обоснование.** Талия честнее отражает висцеральный жир. Вес шумит от воды, гликогена, содержимого кишечника.

**Последствия.** Цель считается достигнутой по талии, даже если вес выше целевого. Замер талии — раз в неделю, натощак, утром.

## ADR-003 — Темп 0.3–0.4 кг/неделю

**Статус:** принято

**Решение.** Целевой темп — 0.3–0.4 кг/нед (~0.4–0.5 % массы тела). Дефицит не превышает 20 % от TDEE.

**Обоснование.** 0.5 кг/нед даёт заметный голод. 0.25 кг/нед растягивает цель на 20 недель — воля кончится раньше.

**Важно.** Голод определяется составом еды, а не размером дефицита. Рычаги: белок 1.8–2.2 г/кг, овощи в каждый приём, ноль жидких калорий. См. `04-content.md`.

## ADR-004 — Фиксированная ротация вместо разнообразия по дням

**Статус:** принято. Заменяет исходную схему «недельный пресет с уникальным меню на каждый день».

**Контекст.** Рассматривался вариант монодиеты для максимального упрощения.

**Решение.** Не монодиета, а **фиксированная ротация**: одно и то же полноценное меню все 7 дней. Один завтрак × 7, один обед × 7, один перекус × 7, один ужин × 7. Ротация меняется раз в 2 недели по кругу, всего 3 ротации.

**Почему не монодиета.**
1. Ломает эксперимент с пищевыми ограничениями — меняет разом клетчатку, жиры, FODMAP, микробиоту. Невозможно понять, что именно сработало.
2. Микронутриенты. Разово безопасно, как режим — нет.
3. Не даёт набрать 145–175 г белка при сохранении клетчатки.
4. Срыв на 4–5 день. Это физиология, а не сила воли.

**Почему ротация решает исходную задачу.** Цель была не «разнообразие», а **ноль решений**. Ротация даёт ноль решений, сохраняя баланс БЖУ и микронутриентов.

**Последствия.**
- Объём контента: ~12 рецептов вместо ~25
- Модель: `day_index` не нужен, ровно 4 записи на ротацию
- БЖУ балансируется один раз на 4 блюда, а не на 28 ячеек
- Спринт контента сокращается примерно втрое
- Нужна кнопка досрочной смены ротации: надоело на 5-й день — лучше переключиться, чем бросить

## ADR-005 — Rails 8 + Hotwire, без отдельного фронтенда

**Статус:** принято

**Решение.** Монолит Rails 8 с Hotwire. Без API + SPA.

**Обоснование.** Четыре вкладки со списками, чекбоксами и таймерами полностью покрываются Turbo Frames. SPA добавит недели работы и ноль ценности при одном пользователе.

---

## ADR-006 — SQLite в проде

**Статус:** принято

**Решение.** SQLite + Solid Queue / Solid Cache. Без Postgres.

**Обоснование.** Один пользователь, единицы запросов в день. Бэкап — копирование файла. Для этого профиля нагрузки это не компромисс, а правильный выбор.

**Последствия.** При выходе на публику — миграция на Postgres. Заложить: не использовать SQLite-специфичный SQL.

---

## ADR-007 — Материализованный список покупок

**Статус:** принято

**Решение.** `ShoppingItem` создаётся записями в БД при создании плана недели, а не считается на лету из рецептов.

**Обоснование.** Нужно править список руками («это уже есть дома», «купил больше») без пересчёта и без потери правок при пересборке.

---

## ADR-008 — Рецепты правятся в файлах, не в админке

**Статус:** принято

**Решение.** Ингредиенты и рецепты хранятся в YAML/CSV в репозитории, заливаются rake-задачей. Админки нет.

**Обоснование.** При одном пользователе админка — чистая трата времени. Файлы дают diff, историю и code review контента.
